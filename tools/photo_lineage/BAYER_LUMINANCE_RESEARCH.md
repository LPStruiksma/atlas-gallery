# Bounded Bayer-to-grayscale bridge — model-free Lane B research

Issue #83. This is a **pure array transform**, NOT an executable RAW/DNG decoder, new model, camera-color pipeline, face recognition, calibrated classifier or device integration. It takes an **already decoded** visible 2D native-endian `uint16` Bayer sensor array and explicit trustworthy calibration supplied by a future independently audited decoder. Does not touch files, devices, metadata, EXIF/GPS, clouds, source photos or cache. No new package dependencies beyond Photo DNA's existing NumPy + OpenCV.

## Why this is an important intermediate safety gate

[rawpy's RawPy API](https://letmaik.github.io/rawpy/api/rawpy.RawPy.html) exposes `raw_image_visible`, `raw_pattern`, black levels and white level, but the raw buffer must remain within the owning open decoder context; changing raw image buffers can even change subsequent postprocessing. The visible pattern can be 1×1/4×4/6×6 or other shapes for non-Bayer sensors; the decoder's black-level list is typically keyed by **color index**, NOT necessarily by sensor-position order. An eventual rawpy adapter must explicitly derive the **four sensor-position black levels**, validate visible CFA alignment, and refuse uncertain orientation/phase, color descriptions, levels or dimensions. Do not directly pass `black_level_per_channel` as if it were row-major.

`bayer_to_grayscale(raw, pattern, black_levels, white_level, max_side=960)` requires a four-letter RGGB/BGGR/GRBG/GBRG CFA, exactly four **row-major sensor-position** black levels below a scalar white level, 2D native uint16, each source side ≥96, ≤12,000 and ≤48 million input pixels. Output is always ≤1024 per side, ≥48 per side or fails closed. Odd input dimensions discard the final unmatched row/column. The four offset CFA color planes are each resized with OpenCV `INTER_AREA` before black/white correction and an approximate fixed linear BT.709-like luma weighting (R .2126, each G .3576, B .0722) with clipping to uint8. No white balance, color matrix, gamma, camera profile, optical distortion, demosaicing, EXIF orientation or image-content-derived histogram stretch. These intentional compromises avoid invisible tuning and may reduce recall; luminance is **a comparison proxy, not a photographic rendering**.

`audit_grayscale_byte_aliases` consumes only **2–10 caller-provided contiguous uint8** bounded grayscale arrays, computes transient SHA-256 bytes and **fails closed** when any normalized preview is identical. Only counts and uncertainty flags are returned; no hashes, identifiers, pixel arrays or paths. Separate different-shutter frames could become identical after quantization; byte-distinct previews still cannot prove separate captures, rights, author, sessions, photo identity or statistical independence. Shape is not encoded in the alias digest, so equal flattened bytes of differently shaped frames conservatively abstain.

## Reproducibility and resource interpretation

```bash
python -m unittest tools.photo_lineage.tests.test_bayer_luminance -v
```

Five synthetic-only cases cover all four CFA patterns and source-byte preservation, differing black levels, area decimation, invalid calibration/input budgets and abstention on duplicate normalized previews. Independent local Linux Python/OpenCV 4.13/NumPy 2.3 host smoke using fictional uint16 arrays: 256² sensor →128² preview in ~1.5ms, 2048×1536→960×720 in ~74ms, and 6000×4000→960×640 in ~77ms. These are **single-process wall-time observations**, not robust p95. Peak process RSS ranged ~110–187 MiB across that *whole process*, not the converter's incremental allocation. No rawpy, decoder decompression, DNG, real photos or Android/S24+ benchmarks were performed. Source image sensor buffers already reside in RAM; preventing a hazardous RAW decode must happen in a *separately approved decoder boundary before data reaches this function*.
