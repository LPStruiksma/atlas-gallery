# Portable Java-8 preprocessing canary for a future Android V5 backend

**Status: pure offline artificial-image infrastructure. No Galaxy S24+
execution, no Android app integration, no model weights, no third-party
photos, no licensed dataset admission and no production authorization.**

This adapter bridges the Python-only
`audit_intel_resize_goldens.py` reference vectors to a reusable
Java 8 class, `IntelSyntheticCanary.java`, which can eventually be
called by an Android experimental resize implementation without importing
Pillow or the OpenVINO graph.

## Why it matters

Intel's pinned Open Model Zoo 0287/0288 Market-1501 evaluation uses
Pillow BILINEAR to 128×256, while its README declares BGR, NCHW
256×128. On synthetic gradients and checker patterns, standard
OpenCV `INTER_LINEAR` frequently disagrees with PIL's
downsampling/resampling semantics. An Android library named
"bilinear" is **not** a substitute for byte-by-byte verification.
The previous Python-only test was valuable, but could not directly
exercise a future Android-native resizer.

## Portable production-independent callback contract

`IntelSyntheticCanary.java` is deliberately plain Java 8:
no Android SDK, photo library, network, reflection, file reads,
image decoders, graphics APIs or ML dependencies.

```java
IntelSyntheticCanary.Result report =
    IntelSyntheticCanary.verify((sourceWidth, sourceHeight, syntheticRgb) ->
        myExistingRgbResizer(sourceWidth, sourceHeight, syntheticRgb, 128, 256));
```

The callback MUST return exactly `128×256×3` **interleaved RGB
uint8 bytes** for the four **generated** synthetic inputs.
The class creates all inputs itself and verifies each generated
source's pinned SHA-256 before invoking the callback. It then checks:

- resized RGB `SHA-256` against the frozen **Pillow 12.3.0** reference;
- BGR, NCHW, raw 0–255 **little-endian float32** packed tensor
  `SHA-256` against a separately pinned exact reference; and
- that both comparisons agree, preventing contradictory source goldens.

It does not run the model or inspect actual user image pixels. The
result provides only `allFourExact`, checked/passing counts, and a
small aggregate JSON string. The output **always** states
`real_model_or_android_runtime_verified=false`,
`production_approved=false`, and `auto_confirm_allowed=false`.
Even all-four byte parity means only a synthetic evaluation-input
step agrees with the frozen reference.

The included `--self-test` CLI deliberately runs a **wrong**
nearest-neighbor resizer: gradient, checker and impulse mismatch,
while identity-shaped colorbars agree. The CLI expects exactly
**one of four** passing, proving the test is fail-closed on
incompatible interpolators. It accepts no paths or photos.

## Independent cross-language positive control

`test_java_synthetic_canary.py` compiles the actual Java source as
`javac --release 8` in a disposable temporary directory, and:

1. Checks the Java-only negative control: 1/4 match and no false green.
2. Generates the four synthetic resized RGB outputs using the
   **pure-Python standard-library** implementation in
   `synthetic_pillow_bilinear_reference.py`. Its outputs were checked
   locally against actual Pillow **12.3.0** byte for byte for all
   four fixed synthetic geometries and independently match the
   previously pinned SHA-256 digests.
3. Writes only those artificial reference bytes to an auto-deleted
   temporary directory. A *test-only* Java adapter reads those exact
   temporary generated bytes, supplies them through the same callback,
   and verifies **4/4 fully matching RGB and BGR float32 tensors**.
4. Flips one bit of one generated RGB fixture, reruns the Java check,
   and requires a drop to **3/4**. No real photo filename or
   personally identifying data is ever involved.

The portable Java canary itself reads **no** files; temporary file
reading exists only in the isolated fictional Python-driven JVM
test harness. **Pillow is no longer required for the positive 4/4
Java test**; only an optional *independent* Pillow comparison test
is skipped when Pillow is absent. The JDK remains needed to compile
the actual Java bridge and is visibly skipped if unavailable.
The CI workflow remains unchanged, using the JDK already present.

The pure-Python source deliberately accepts ONLY the four existing
registered artificial source-pattern names and source dimensions.
It reproduces Pillow's versioned two-axis triangular/bilinear
antialias weights and **22-bit fixed-point per-pass rounding** for
the exact test matrix; it is *not* a production image resizer,
a general guarantee of parity across arbitrary photos/Pillow releases,
or a verified Android decoder. Frozen hashes, not matching function
names, are the ground truth for this synthetic protocol.

### Run on a local development host, no device required

```sh
cd tools/identity_fusion
python -m unittest test_java_synthetic_canary -v
javac --release 8 IntelSyntheticCanary.java
java IntelSyntheticCanary --self-test
```

These are local/host development commands. The generated `.class`
files should not be committed or packaged in an APK.
