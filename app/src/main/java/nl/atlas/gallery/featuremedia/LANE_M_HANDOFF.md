## Media API (backward-compatible trailing record fields)

- `MediaRecord.volumeName` = actual `MediaColumns.VOLUME_NAME`; never identify items by bare `_ID`. The repository now builds per-row **volume-specific** item URIs from `MediaStore.Images/Video.Media.getContentUri(volume)` (once per mounted-volume collection). If a query row has a missing/unmounted volume, it is omitted rather than accidentally reusing an ambiguous aggregate URI. `mediaIdentity()` includes URI, volume, type and ID. `absolutePath` keeps the primary V4 convention `/storage/emulated/0` but maps named secondary volumes to `/storage/<volumeName>`, preventing SD/primary filename collisions. This remains a legacy V4 location hint, **not** a stable identity: no filename guesses or automatic moves reconciliation.
- `providerVersion` = `MediaStore.getVersion(context, specificVolume)`, captured once per volume; `generationModified` = per-item `GENERATION_MODIFIED`. Scan rejects a change in provider version between start and end. API 29 or unknown versions deliberately returns **no reusable cache key**.
- `widthPixels`, `heightPixels`, `orientationDegrees` (including video) and `displayAspectRatioOrNull()` give Lane G a ratio *hint*, not decoded-orientation truth for every format. Invalid dimensions return null; never force a square into a real-ratio row.
- `isFavorite` reads MediaStore `IS_FAVORITE` on API 30+ and `favoriteKnown` distinguishes null/unavailable from an explicit false; unknown must be treated conservatively for Declutter.
- `takenAtMillis`/ `dateSource`: captured date, strictly parsed named camera/WhatsApp filename, file modified time, then date added. Filename-derived time uses device timezone; DST gaps and impossible calendar dates fall back. No EXIF writes.
- `presentationCacheKeyOrNull(pixels, catalogueEpoch, editorRevision)` hashes **none** of the private bytes and only accepts a known provider version + generation. The integrator must pass a monotonically fresh publication/access epoch, only call for visible cells, and never treat a key as read permission.

## MediaStore orientation overflow is not legitimate screen geometry

The Android 35 MediaStore specification describes `ORIENTATION` as quarter-turn integer degrees. M's catalogue previously executed `cursor.longOr(idxOrientation).toInt()` without checking bounds. A malformed 64-bit value like `4294967296L` would wrap to zero and be displayed as if the item were unrotated, while `4294967386L` would wrap to 90° and swap width/height. New pure `mediaOrientationDegreesOrInvalid(raw: Long)` preserves every in-range `Int` (including valid wrapped degree values) but maps out-of-range provider values to an invalid sentinel `Int.MIN_VALUE`; `displayAspectRatioOrNull()` then correctly yields no ratio rather than manufacturing gallery geometry. This does not alter normal 0/90/180/270 previews. Committed `MediaMetadataTest.orientationConversionDoesNotWrapCorruptProviderLongIntoValidDegrees` checks 8 in-range and 6 over-range values. This is pure-JVM-source test coverage, **not** an Android MediaStore integration run.


## Reject implausible 64-bit provider dimensions (24 October)

MediaStore widths/heights are integer pixel dimensions. The previous M cursor ingest used `coerceIn(0, Int.MAX_VALUE).toInt()`, turning an invalid/malformed `Long.MAX_VALUE` provider field into a *fabricated* 2,147,483,647-pixel image. For original-proportions grid this can produce an absurd aspect ratio or huge row geometry instead of using the safe unknown-ratio layout. The new pure `mediaPixelDimensionOrUnknown(raw: Long)` admits only 1…`Int.MAX_VALUE`, otherwise records **0 (unknown)**; `displayAspectRatioOrNull()` already returns null when either dimension is nonpositive. This leaves normal MediaStore dimensions unchanged and makes malformed raw provider metadata incapable of producing invented giant panoramas or portrait rows.

## Final scan-publication admission fence (24 October)

**Release-relevant race closed:** M's `GalleryRepository.load()` already compares volume-specific MediaStore provider versions and generations before returning results. Previously, the ViewModel accepted an inventory after the repository returned using **only** `refreshQueue.mayPublish(ticket)`. A provider ContentObserver notification, permission-bit transition, or explicit revocation that happened after the repository's final version/generation comparison but before the main-thread StateFlow assignment could let an obsolete catalogue appear as a new publication epoch. For reviewed People and a 150k archive, this must not happen.

M now owns `featuremedia/GalleryScanPublicationAdmission.kt`, a pure constant-time double fence. Immediately before `GalleryPublishedInventory(ticket,inventory,observedGrantAtStart)`, the ViewModel reads the **current live Android permission bits** and the atomic observer revision and requires: latest active request, not explicitly revoked, positive current and start access, identical start/end grant, and identical start/end provider notification revisions. There are **no suspensions** between that check and the StateFlow publication. A rejected snapshot cannot enter UI/People/Albums caches. The prior valid publication remains but `inventoryDirty` is set. If the **grant stayed unchanged** and only MediaStore changed, the ViewModel queues a **single** automatic follow-up scan; `lastAutomaticallyRetriedTicket` prevents unbounded repeated automatic scans on a continuously changing provider. If grant bits changed/revoked, no automatic provider access occurs; Activity owns the regrant/selected-photo rescan flow.

**Important limitation:** Android 14+ selected-photo re-selection may change accessible URI membership while ALL permission flags remain identical and no provider observer fires. This final fence does not invent information: the existing Activity `invalidatesGallerySnapshotOnResume`/fresh selected-grant ticket is still required.
